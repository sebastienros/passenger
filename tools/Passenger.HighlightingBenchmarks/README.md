# Passenger: TextMateSharp → Tint experiment

This benchmark calls Passenger's real `Highlighters.For` / `TextMateHighlighter`, waits for its background work through a queued `SynchronizationContext`, and edits its real `TextDocument`. It is not an isolated regex benchmark. It does not start the IDE, render frames, launch language servers, or measure whole-IDE startup or typing latency.

See [measured results and tradeoffs](RESULTS.md), and the follow-up [production instrumentation and stage attribution](INSTRUMENTATION.md).

## Versions and scope

- Upstream: `Zaneris/passenger` commit `97758c1ac1d198b02b7ac2282d3c1018f0023282`.
- Baseline: TextMateSharp 2.0.4 and its pinned Onigwrap dependency.
- Candidate: Tint 0.1.2 (source commit `b72ea69c28cf5ef3d919bd7f625c5da24c9ccb37`) with GregsEx 0.5.3.
- Release build, .NET SDK `11.0.100-rc.3.26522.148`, runtime `11.0.0-rc.3.26522.148`, macOS 15.8, arm64, Apple M4 Pro, 48 GiB RAM.
- Tint loads Passenger's existing embedded grammar JSON, recursively registering dependencies. No bundled Tint grammars, generated kernels, or hot-pattern compilation are used.
- Existing scope-to-TokenKind mapping, grammar normalization, YAML key policy, per-grammar locking, long-line cutoff, one-second line budget, background scheduling, and incremental line tables are retained. C# still uses Roslyn.

## Method

`cases.json` records each fixture's upstream path and repetition count. Fixtures are copied from that upstream commit; SCSS and Less come from its colour tests. Each fixture is repeated to about 10,000 lines. These are intentionally synthetic large documents made from actual Passenger sources, not a representative survey of users' projects. The runner normalizes CRLF and adds a separating newline identically for both engines. Each output records the exact expanded input SHA-256.

Three fresh processes per engine and workload run sequentially, with engine order reversed in the second round. Each process measures:

1. The first highlighter construction and complete pass, including lazy grammar/theme loading and tokenizer JIT ("cold"). File reading and `TextDocument` construction precede measurement; this is **not process startup time**.
2. Two further warmups, then seven measured complete passes. The tokenizer stays cached as it does in Passenger; each pass creates a new highlighter and line table. Full GC runs before each pass, outside the measured interval.
3. Six batches of 100 alternating one-character replacements in the middle of the document. The first batch is discarded. Each edit waits until the incremental pass has landed. This includes document rewrite and background dispatch, but not GUI input or rendering. Timing each batch avoids per-edit process-counter overhead.

Tables use the median within each process, then the median of the three process medians. Raw samples are under `results/`; `summary.json` and `tables.md` are generated by `summarize.py`.

Wall time uses `Stopwatch`; CPU is the process's total processor-time delta (all threads, including JIT and GC); allocation uses `GC.GetTotalAllocatedBytes(true)` (all managed threads). GC collection deltas are captured inside full-pass intervals. Working set and lifetime peak working set are sampled after a forced GC at the end of each full pass; these include runtime, JIT, managed heaps, native allocations and loaded libraries. Peak working set is cumulative, not per-operation. Allocation savings do **not** imply equal RSS savings.

The exploratory raw `retainedBytes` counter is a before/after managed-heap delta, not a live-object census: prior completed tasks can remain rooted until the next worker invocation. It is deliberately excluded from comparisons and should not be interpreted as the size of the highlighter's cache.

Every pass hashes its complete `(start, length, TokenKind)` sequence. Repeated full passes must match; every edit batch restores the original text and must match a fresh pass. `summarize.py` separately compares input and colour hashes across both engines and all three processes. Existing colour tests additionally exercise edits that change multiline state, brace/tag matching and responsiveness.

## Reproduce

Build the benchmark in two separate checkouts: the pinned baseline with this `tools/Passenger.HighlightingBenchmarks` directory copied in, and the candidate branch. Do not run the two builds or measurements concurrently.

```sh
AVALONIA_TELEMETRY_OPTOUT=1 dotnet build tools/Passenger.HighlightingBenchmarks -c Release
python3 tools/Passenger.HighlightingBenchmarks/run.py \
  --baseline /path/to/baseline/artifacts/bin/Passenger.HighlightingBenchmarks/release/Passenger.HighlightingBenchmarks.dll \
  --candidate /path/to/candidate/artifacts/bin/Passenger.HighlightingBenchmarks/release/Passenger.HighlightingBenchmarks.dll
python3 tools/Passenger.HighlightingBenchmarks/summarize.py
```

The baseline needs the same benchmark code, but its original central package versions and production source. Regenerate the **benchmark project's** lock file when building it against baseline; production locks remain those of the selected commit. `--dotnet /path/to/dotnet` selects a particular runtime host.

## Limits

These results describe one machine and this corpus. They do not establish a whole-IDE CPU or RAM reduction, concurrent-document throughput, adversarial regex behaviour, or universal TextMate compatibility. Warm RSS reflects allocator/cache retention and can increase despite much lower allocation. A rendered IDE check and the targeted tests supplement the corpus comparison; the complete cross-platform CI suite is not run here.
